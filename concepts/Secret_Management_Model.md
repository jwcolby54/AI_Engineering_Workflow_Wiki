# Secret Management Model

## What This Is

A short explainer of how secrets work across every project on this machine
that shares local infrastructure (Postgres, Vault). It exists because the
three layers involved -- LastPass, Vault, and the Windows Credential
Manager (keyring) -- are easy to blur together, and re-deriving the
relationship per project wastes time and produces inconsistent setups.

For the full mechanics, exact commands, and a worked example, see
`standards/shared_infrastructure_standards.md`'s "Secret Management Model"
section. This page is the conceptual summary; that document is the
operational reference.

## The Three Layers

1. **LastPass** -- human-durable storage for the small set of foundational
   secrets nothing else can regenerate (Vault's unseal key and root token,
   a scoped read-only migration token, the Postgres superuser password).
   JWC looks these up when prompted; he does not invent secret names or
   values, and the AI does not invent them either -- they were established
   once, at bootstrap time.

2. **Vault** -- the runtime credential authority. For database access,
   Vault does not store a password at all. It stores a connection
   definition (`database/config/<project>`) and a role definition
   (`database/roles/<project>-readwrite`) describing exactly how to mint a
   brand-new, time-limited PostgreSQL login on request, and how to tear it
   down afterward. The minted login is a temporary member of a permanent
   `NOLOGIN` PostgreSQL base role (`<project>_readwrite_base`) that holds
   the actual grants -- the base role itself can never be logged into
   directly.

3. **Windows Keyring** -- a local, transient cache of whatever Vault most
   recently issued to this machine, so an application doesn't have to
   re-authenticate to Vault on every single run. It holds no long-term
   truth; if wiped, the worst case is one extra Vault round-trip.

## The Rule

JWC is a secure storage/retrieval point, never a generator of secret names
or values, in either direction:

- An **existing** secret gets requested by name (via
  `E:\DevPython\LocalVaultOperator\vault_operator.py prompt-secret`) and
  JWC pastes it in from LastPass.
- A **brand-new** secret -- which should be rare, since Vault's dynamic
  database credentials mean most projects never need a static password at
  all -- gets its name and value generated by the AI and handed to JWC
  once, for him to store.

## Two Vault Token Classes

- `SA_SECRET_VAULT_ROOT_TOKEN` -- admin-class, required to write
  `database/config/*` / `database/roles/*`. Used rarely, only during
  setup.
- `SA_SECRET_VAULT_DEV_MIGRATION_TOKEN` -- read-class, sufficient for
  routine `database/creds/<role>` reads at application runtime. Documented
  as unable to perform admin setup operations. This is what running
  application code should use day to day.
